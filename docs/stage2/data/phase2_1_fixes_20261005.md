## B1 — Special NSE sessions

### The problem
Phase 2 archived Monday–Friday only. NSE sometimes trades on a Saturday or Sunday (budget day, Muhurat trading, disaster-recovery sessions). Those sessions were missing, so a Friday → Monday return in RET-1 was treated as an ordinary one-session return even when a session lay between.

### What was archived
- Every Saturday and Sunday from 2005-01-01 to 2026-09-30 was requested from NSE: 2,270 days.
- **27 have a bhavcopy** (a session took place). 2,243 have no file (HTTP 404, recorded). 0 were left unattempted.
- 2,322 records were appended to `data/stage2/raw_manifest.jsonl` (2,292 × 404 and 30 × 200; three 2024 dates exist in both the legacy and UDiFF formats). The first 5,844 records are the unchanged Phase 2 state.
- Command: `python3 -m src.stage2.archive bhavcopy-weekends 2005-01-01 2026-09-30`.

### Retries for transient errors
`src/stage2/archive.py`: an HTTP 5xx or 429 is now raised instead of recorded. The caller retries up to 4 times (5 s, 10 s, 15 s waits). If all fail, nothing is written to the manifest, so the next run tries again. Before this change a 503 would have been stored as a permanent "no file". The Phase 2 manifest contains only 200 and 404 statuses, so no earlier session was lost this way.

### Classification
`session_type` in PANEL-1.1 (`src/stage2/panel.py`):

| Value | Meaning |
|---|---|
| `STANDARD` | Monday–Friday session |
| `SPECIAL_WEEKEND` | Saturday or Sunday session |

The 27 special sessions are listed in `data/stage2/panel/special_sessions.csv` with source file hash, row count and neighbouring standard sessions. 8 are before the verified period; **19 fall inside it** (2011-06-22 → 2026-09-30).

Evidence that these are real sessions: for all 27, the next session's NSE `PREVCLOSE` equals the special session's close for 100% of common symbols, and equals the earlier Friday close for only 0–7%.

### Calendar QA
`calendar_check(..., weekends=True)` runs the same completeness check on weekend days that Phase 2 ran on weekdays: every day must be either a downloaded session or a recorded 404. The build script fails if any weekend day was never attempted. Result is stored in `data/stage2/panel/panel1_1_manifest.json`.

### UNIV-1: unchanged
UNIV-1 liquidity windows keep the existing standard-session definition. `universe.py` was not edited. The build script rebuilds UNIV-1 from standard sessions only and checks the hash against the frozen value.

### RET-1.1: session continuity
Rule applied (as instructed): a return that spans a special session is flagged, not treated as an ordinary consecutive-session return.

- Special sessions are never return endpoints. RET-1.1 has the same 6,115,762 rows as RET-1.
- New column `spans_special_session`: true when a special session lies strictly between `prev_date` and `date`.
- New status `SPECIAL_SESSION_SPAN`, placed after `MULTI_SESSION_GAP` in the rule order. It is **not research-grade**: `ret_research` is NaN. `ret_raw` is still reported.
- 32,742 rows span a special session. 2,633 were already `MULTI_SESSION_GAP`; **30,109 get the new status** (0.49% of rows), on 19 dates.

### Known limits
1. **Weekday special sessions are not separated.** A Muhurat session on a weekday holiday (for example 2021-11-04, 2022-10-24, 2024-11-01) has a bhavcopy, was already in PANEL-1, and stays `STANDARD`. It is a return endpoint, so return continuity is correct. It also counts as one session in UNIV-1 windows, exactly as in frozen UNIV-1. Telling these apart needs NSE holiday circulars for every year, which are not archived.
2. **Two very small weekend files** are kept as special sessions because NSE published a file: 2010-05-16 (7 EQ rows, before the verified period) and 2012-11-11 (14 EQ rows). The second one flags all 1,378 Friday → Monday returns of 2012-11-12. This is the conservative side of the rule.

## I1 — Large corporate-action residuals

### The problem
CA-2 validates a bonus or split when the factor explains the price move to within 25%. RET-1 then marked such rows `ADJUSTED_VALIDATED` and research-grade, even when the adjusted return left over was large.

### Treatment (RET-1.1)
- New status `VALIDATED_LARGE_RESIDUAL`: a validated bonus/split whose adjusted return is beyond **10%** either way (`LARGE_RESIDUAL = 0.10` in `src/stage2/returns.py`).
- It is **not research-grade**: `ret_research` is NaN. `ret_raw`, `ret_adj`, the factor and the event text are all kept on the row.
- No new adjustment is made and no factor is changed. Raw prices are untouched.
- These rows count as unresolved in `ret1_1_entity_quality.csv`.

### Result
- **106 rows**, 104 entities. Listed in `data/stage2/returns/ret1_1_large_residuals.csv`.
- By event: 56 split, 41 bonus, 9 bonus+split.
- Residual range −14.4% to +21.0%; 93 positive, 13 negative.
- 24 rows belong to 23 entities that were ever UNIV-1 members.

## Review decisions (approved 2026-10-05)

These five decisions are fixed. They are recorded here so that none of them exists only in conversation.

1. **Large-residual threshold = 10%, fixed.**
   - `LARGE_RESIDUAL = 0.10` in `src/stage2/returns.py`; also stored in `data/stage2/returns/ret1_1_manifest.json` under `parameters.large_residual`.
   - It is a **predefined diagnostic / research-quality rule**, set before any Stage 2 research and not tuned on any result.
   - `VALIDATED_LARGE_RESIDUAL` is a research-quality exclusion flag. It is **not** evidence that the corporate action is invalid: the NSE record still validates under CA-2.
   - No raw price and no corporate-action factor is changed.
2. **`SPECIAL_SESSION_SPAN` rows stay excluded.**
   - `ret_research` remains empty on these rows. They are not restored to recover the ~0.49% of observations.
   - **"Research-grade" means a row passes the predefined data-quality rules. It is not proof that the underlying market history is free of error.**
3. **Weekday special sessions: classification left unresolved.**
   - This is a **calendar-source limitation**: official NSE holiday/session circulars for past years are not archived, so a weekday special session (for example Muhurat trading on a weekday holiday) cannot be identified from evidence.
   - No `session_type` is guessed. In PANEL-1.1, `STANDARD` on a weekday therefore means "weekday session, special status not determined".
   - The observed session is preserved as it is: not deleted, not altered.
   - UNIV-1 is not changed because of this.
4. **2012-11-11 is kept.**
   - The 14-row weekend file stays a special session. Nothing is discarded on the basis of row count.
   - The conservative `SPECIAL_SESSION_SPAN` flag on the 1,378 returns of 2012-11-12 stays.
5. **Reproducibility entry point.**
   - `scripts/build_stage2.py` is the deterministic rebuild entry point, with all 150 hash/count checks.
   - The ~7 minute / ~10 GB run is not optimised; it would only be changed for correctness.
